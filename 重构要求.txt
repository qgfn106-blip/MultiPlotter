（1）功能代码轻量化，并且分散开，避免代码阅读过难
multiplotter/
    __init__.py
    core.py              # MultiPlotter 基础状态和公共接口
    builder.py           # PlotBuilder
    styles.py            # rcParams 和主题
    validation.py        # 数组、网格、表格等校验
    draw_2d.py           # 二维图层
    draw_3d.py           # 三维图层
    vector_fields.py     # quiver、streamplot、stream3d
    tables.py            # 表格和单元格样式
    animation.py         # AnimationPlotter
    saving.py            # 保存路径和 writer

按照这个结构重新构造代码，并且保证类方法原有功能不受影响，且专门写一个py文件以及提供一个接口对于科学研究具体算法与绘制的时候可以组合各种类方法，在add_"kind"模块中尽可能避免过于复杂的绘制方法统一，并且以简单的对流传热模拟为例子(作为md里的示例)

（2）将_draw_layer中的巨大if/elif 改为建立绘制器注册表，如：
DRAW_HANDLERS = {
    "line": draw_line,
    "scatter": draw_scatter,
    "surface": draw_surface,
}
避免代码过于臃肿，并且方便代码测试与修改

同样在add_layer以及add_plot中也可以尝试这种注册化

（3）config图层配置中依赖大量字符串键，可能类型安全不足，看看是否可以实现将公共配置和图层专属配置分离，但是还是要优先保证代码的可读性，便于修改，并且与matplotlib里绘制的原方法的参数设置一致的原则

（4）全局 matplotlib.rcParams 修改会产生副作用，matplotlib_option() 和 matplotlib_surface_option() 会调用plt.style.use("default")
plt.rcParams.update(...)，可能会出现一些问题如：修改整个 Python 进程的全局绘图配置；可能覆盖用户在外部设置的 Matplotlib 风格；多个 MultiPlotter 对象之间会互相影响；在多线程或服务端环境中存在竞态风险；一个绘图对象不能真正独立拥有自己的样式；用户在调用 draw() 前设置的 rcParams 可能被覆盖。

建议：
1. 使用 matplotlib.rc_context() 临时应用样式；
2. 将样式作为实例级配置保存；
3. 尽量直接对 Figure 和 Axes 设置属性；
4. 提供 theme 参数，而不是无条件调用 plt.style.use("default")；
5. 明确是否允许覆盖用户全局样式；
6. 文档中说明样式的作用域和生命周期。

(5)使用 plt.savefig() 而不是 fig.savefig(),由于：
多个 Figure 同时存在时保存错图；
用户在绘制过程中切换当前 Figure 后产生意外；
在测试环境或嵌入式环境中行为不稳定；
不利于线程安全和对象化管理。

(6) clear() 的生命周期管理不完整
MultiPlotter.clear() 会清空配置和坐标轴记录，但没有明确关闭旧 Figure，也没有处理动画状态。
对于 AnimationPlotter，如果已经创建过动画，再调用继承来的 clear()，可能留下：
- 旧的 Figure 引用；
- 旧的 Axes 引用；
- 旧的动画对象；
- 旧的事件源；
- 与新配置不一致的内部状态。
建议：
- MultiPlotter.clear() 提供是否关闭 Figure 的策略；
- AnimationPlotter.clear() 覆盖父类方法，先调用 stop_animation()；
- 明确 draw() 多次调用时旧 Figure 是否自动关闭；
- 提供 close() 方法；
- 文档说明对象的生命周期。

(7)透传白名单可能与 Matplotlib 版本变化脱节
建议：
- 明确哪些参数是框架参数，哪些参数会透传；
- 避免维护过大的手工白名单；
- 对确实需要完全透传的图层，使用专门的 mpl_kwargs 字典；
- 加入 Matplotlib 版本兼容策略；
- 在测试中覆盖常见参数和不同版本行为。

(8)配置默认值存在重复维护
默认值分散在多个地方：
- add_* 方法的函数默认参数；
- KIND_DEFAULTS；
- INIT_STYLE_DEFAULTS；
- PASSTHROUGH_KEYS；
- 各类方法内部的默认处理；
- README 中的预设说明。
这容易产生文档和代码不一致。例如 README 中对某些默认行为的描述，需要和源码中的 KIND_DEFAULTS、实际 add_* 签名同时保持一致。
建议：
- 将默认值集中到一个结构化定义中；
- 由该定义生成文档或至少生成测试；
- 避免同一默认值在多个地方重复写；
- 为每个 kind 增加默认值快照测试。


（9）README篇幅过长，信息密度不均
建议拆分为：
README.md              # 快速开始和核心概念
API.md                 # 所有方法和参数
ANIMATION.md           # 动画
EXTENDING.md           # 扩展开发
examples/               # 完整示例
FAQ.md                  # 常见问题
README 开头建议只保留：
1. 安装；
2. 最小二维示例；
3. 最小三维示例；
4. 最小动画示例；
5. 链接到详细文档。


(10)“完全兼容 Matplotlib 参数”的表述需要收窄
README 中对 **kwargs 的描述比较绝对，容易让使用者理解为所有 Matplotlib 参数都可以原样透传。但源码实际上存在白名单和特殊参数处理。
建议改成更准确的表述：
支持透传目标 Matplotlib 方法的大部分常用参数；框架自身参数与部分版本相关参数由 MultiPlotter 单独处理，具体以对应方法签名和参数表为准。

(11)新增一个图层需要修改多个类属性和方法，这说明扩展成本仍然较高。文档虽然把步骤写清楚了，但开发者仍然容易漏改某个注册表。

建议将扩展流程设计成单一注册操作，至少提供类似：
register_layer(
    kind="step",
    dimension=2,
    add_method="add_step",
    draw_handler=draw_step,
    defaults={...},
)
这样文档可以从“修改七个位置”简化为“实现方法并注册”。


缺少扩展契约的可执行校验
文档提到 config 字段缺失会触发 KeyError，但更好的方式是新增图层时立即验证：
- 是否有 kind；
- 是否有 dimension；
- 是否有 subplot；
- dimension 是否为 2 或 3；
- 处理器是否存在；
- 默认参数是否可调用；
- 动画模式是否声明。
建议提供 validate_layer_config() 或注册时校验机制。

缺少版本兼容和 API 稳定性说明
扩展开发者需要知道：
- 哪些类属性可以覆盖；
- 哪些方法属于稳定 API；
- 哪些方法是内部实现，未来可能变化；
- Matplotlib 版本支持范围；
- 新增图层是否需要同步测试。
建议在文档中明确标记：
公开 API
扩展 API
内部 API
实验性 API

(12)使用时需要特别注意的地方
1. 不要在同一个 subplot 中混用二维和三维图层。
2. add_*() 阶段主要是登记配置，真正绘制要等到 draw()。
3. 动画的 reset 模式会清空坐标轴，回调函数必须重新绘图。
4. 使用 artists 模式时，必须获得正确的 Matplotlib artist，并返回需要重绘的对象。
5. 三维动画通常不能使用 blit=True。
6. 动画数据变化较大时，应显式设置 xlim、ylim、zlim，否则可能出现范围跳动或直接报错。
7. 使用 init() 时，未列入白名单的参数可能被过滤并只打印警告，不一定直接抛异常。
8. 使用 **kwargs 时，要区分 MultiPlotter 自己的参数和底层 Matplotlib 参数。
9. 同时创建多个绘图对象时，要警惕全局 rcParams 和 pyplot 当前 Figure 的相互影响。
10. 如果重复调用 draw()，应明确旧 Figure 是否需要关闭，避免长期运行时资源积累。
11. 表格、三维流线和高密度矢量场可能消耗较多内存和计算时间。
12. 依赖 Matplotlib 具体版本的参数不能简单假设在所有环境中都可用。
13. 如果开发新图层，不能只修改 SUPPORTED_*_KINDS，还必须同步考虑添加入口、绘制分派、默认参数、透传参数和动画行为。
14. config 字典字段是内部契约，字段名变更必须同步修改所有相关方法和测试。
15. 不建议把这个单文件直接当作稳定公共库发布，最好先完成模块拆分、测试补齐和 API 收敛。
